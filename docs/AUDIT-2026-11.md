# Audit: what Agentic Lab claims and what it does (November 2026)

An audit of commit 145b859 (main, 2026-11-17), run in an isolated copy of the repository with a real model (qwen2.5:7b and nomic-embed-text on Ollama), throwaway Postgres, Redis and Qdrant, and a logging proxy between the lab and Ollama, so every prompt, tool list and reply quoted here comes from a log. It is the baseline for the rebuild on `feat/topology-lab`: every claim the README, the docs, the UI and the project's page on destbreso.com make, set against the code and against runs. The claims of the first foundations document are quoted from [FOUNDATIONS-v1.md](FOUNDATIONS-v1.md); [FOUNDATIONS.md](FOUNDATIONS.md) now states them as hypotheses.

The headline: there are three separate orchestration paths. The one most people meet, the chat agent, which also drives the benchmarks, offers the model no tools, never touches the core engine, and has nothing that limits what each loop sees. The core engine does make real tool calls and honours a per-node model, tools and skills, but only the builder reaches it, and there three of the six built-in recipes fail before their first cycle.

## The three checks of the first foundations

**What is measured and what is written by a model.** In core's signals (the chat path has no signals; each loop just reads the earlier loops' text):

| Signal | Measured by the system | Written by a model |
|---|---|---|
| `execution_result` | `toolCallCount`, `iteration` | `responseText`, the whole narrative |
| `tool_calls` | names, results (500 characters), durations | the arguments the model chose |
| `token_usage` | every field | none |
| `evaluation` | `automatedChecks`, always empty: no path configures checks | `verdict`, `evidence[]` |
| `eval_metrics` | `checksTotal` and `checksPassed`, always 0 | `verdict`, `confidence` |
| `corrections` | none | `corrections[]` |
| `critic_feedback`, `stagnation_alert`, `intervention` | heuristic issues, when the model is skipped | `feedback`, `status`, `reasoning`, `type` |
| `refinement_decision` | `round`; `passRate`, computed from model verdicts | `action`, `reason`, `criticFindings` |
| `plan`, `task`, `strategy` | none | the whole response |
| `compressed_context`, `memory` | none | summaries |

Every field that drives convergence, correction or planning is written by a model. The only measured inputs are token counts and tool-call metadata.

**Whether the executor can touch the tests the evaluator trusts.** Nobody writes the checks: `checks` is never set, so the evaluator's "reality" is whatever its own model decides to run, if anything. In the builder and the Full Pipeline, executor and evaluator both get the full toolkit (`file_write`, `shell`, `git`) in the same working directory, so nothing stops the executor writing or editing tests, and the evaluator can change the world it is verifying. Core's evaluator sees neither the task nor the specification, only the executor's claim, and not even that when the executor hits the tool cap. The chat evaluator sees the task and the output text, and has no tools.

**Whether the critic's restriction is enforced.** Only by what the critic's own prompt builder chooses to read (`critic.ts:218`). The wire carries the full content, and `recentSignals` and the blackboard expose everything to any node. It is a hybrid: heuristics always run, and the model is skipped only while the heuristics are clean and the activity log has fewer than 3 entries (`critic.ts:201`); after that every firing is a model call. Its heuristics are crippled as wired: in the Full Pipeline `tool_calls` never reaches the critic, so it always sees no tools and its stagnation alarm fires falsely after 5 entries; it reads the verdict from `evaluation` signals while the wire delivers `eval_metrics`, so it always shows no verdict. In the chat path the critic is a plain model call over the full content.

## Robustness

- **Failures.** No default output limit and no per-call timeout: the CLI hung for over 7 minutes on one generation. The Ollama provider never passes the abort signal to its client (`ollama.ts:39-51`), and AgenticLoop passes none either, so Ctrl+C did not stop the CLI. A node timeout races the node (`pipeline.ts:717`) but leaves it running; `stop()` does not abort calls in flight; `NodeContext` has no signal. A failed node is marked failed and skipped for the rest of the run (`pipeline.ts:539, 771`). An executor that hits `maxToolRounds` emits no result and still reports success. The chat path marks every run `success: true`, even when every loop throws. Junk from the evaluator becomes "converged" in chat and "inconclusive" in core; no path treats it as a failure. A provider that is down entirely was not tested.
- **Security.** The 28 API routes have no middleware and no authentication, and Next listens on every interface, so `POST /api/pipelines/run` gives anyone on the network a shell-capable agent in the server's working directory. The shell tool's `cwd` argument escapes the workspace (`shell.ts:47`); child processes inherit the whole environment, API keys included (`shell.ts:84`); the blocklist misses `rm -rf ~`, `rm -rf ..`, `curl ... | bash` and interpreters. The file tools are properly contained. A default database password is hard-coded in `storage/factory.ts`.
- **Tests.** `npm test` exits 1, because the CLI and web packages have no test script; core passes 233 tests in 26 files. Nothing covers a built-in recipe, the chat route, the builder route or the CLI. `tsc` excludes test files; including them shows 44 type errors in the test mocks.
- **Types.** `tsc --noEmit` is clean for core, CLI and web.

## What a person can explore today

- Comparing two variants of a team on one task: only through Benchmarks, which means built-in recipes on the chat path, 13 fixed problems (in Spanish), one model for every contender and the judge, one sample, no custom tasks and no saved pipelines. Builder runs are not stored, so builder variants cannot be compared at all.
- Changing what a role sees: not in chat. In the builder, only by topology and wire filters; nothing can remove a field from what an edge carries, and every node still gets `recentSignals`.
- Swapping a role's model: yes in the builder; no in chat, the CLI or benchmarks.
- Limiting rounds: chat's 3 is a constant and the builder's maxCycles is fixed at 10; the gate's threshold and maximum rounds are not exposed; a node's maxIterations and delayMs are ignored.
- What a run stores: each loop's output text (up to 5,000 characters), total tokens booked as output, and `config {recipe, mode}`. Not what each role was given, the topology, the model per node, the split of input and output tokens, a seed, repetitions or a baseline.

## The ten gaps that matter most

1. **One orchestration path.** The chat agent and benchmarks bypass the core, and the CLI runs only the single loop. The chat route becomes a thin adapter over `AgentSession`, and benchmarks and the CLI run through it.
2. **Built-in recipes that instantiate, and loop-backs that work.** Recipe ports derived from the node types; every built-in recipe tested end to end with a scripted model; the executor reading corrections; convergence and backtracking controlling the run; the planner given the task.
3. **No evidence must stop meaning a pass.** Unparsed, partial or inconclusive evaluations block convergence and show as failures, with structured verdicts per criterion.
4. **Real ground truth for the evaluator.** Checks derived from the task and the specification, run where the executor cannot write; separate tools for executor and evaluator; a verdict that must cite tool output.
5. **What each role sees, enforced by structure.** Field allow-lists per wire, provenance on every value (measured or written by a model), no global `recentSignals`, and a record of what each role saw.
6. **Runs as experiments.** One run record for every path: the topology, each role's inputs and outputs, models, the token split, a seed; and a runner for repetitions with the single-loop and best-of-N baselines.
7. **Benchmarks that measure.** Isolated memory, a separate judge model, repeated samples with their spread, tasks a machine can check, quality against cost, and no -1 scores averaged in.
8. **Robust loops.** A default output limit and per-call timeouts, an abort signal through `NodeContext` and every provider, explicit failure on the tool cap and on failed nodes, and honest success flags.
9. **Security.** Localhost by default with token authentication, sandboxed tools, a scrubbed environment for tools, and an allow-list for the shell instead of a blocklist.
10. **An interface built on real events.** One run view fed by the engine's event stream with no synthetic steps; model and provider lists from the API; a layout that fits 1440 px; Settings that save; one set of colour tokens; English strings.

## Not checked

Cloud providers (no keys); Prometheus and Grafana; Adversarial Duel and Supervised Coder in chat (read, not run: their two agents get identical prompts on the same model, so they differ only by sampling); the Full Agent Pipeline with a real model (run only with the mock); memory aggregation, bank cloning, the CLI's chat REPL, skills loaded from SKILL.md files on disk, behaviour with a provider down, retries under real failures, and phone widths. The logs and captures of this audit were kept on the auditing machine only, not in the repository.
